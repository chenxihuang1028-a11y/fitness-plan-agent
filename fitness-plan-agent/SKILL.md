# Fitness Plan Agent

把"收藏了从不看"的健身视频，转成一份真正能照着练的训练计划。核心逻辑：**抓取 → 识别 → 查重/冲突过滤 → 更新计划**。所有数据存在本地文件里，不依赖任何数据库或服务器。

**最终交付物有两份，内容永远保持一致**：
- `CURRENT_PLAN.md` —— 纯文字版，随时能在对话里贴出来看。
- `plan.html` —— **一个单页应用**，发布成 Artifact 给用户一个可以直接打开的链接（用 Artifact 工具发布，同一个文件路径重新发布即可保持同一个 URL，不用每次生成新链接）。顶部两个切换标签：
  - **"查看计划"**：带人体部位示意图的可视化训练计划。
  - **"编辑档案"**：建档/改档案的表单，切换过去会**直接从页面里已有的 `PROFILE` 数据自动预填**（不是从零重填）。这两块共用一个文件、一份 CSS/JS，不是两个分开的 Artifact。

每次处理完一批新链接，这两份文件要么被更新（新动作匹配上了），要么保持原样（新动作不匹配，只是存进了动作库，但 `CURRENT_PLAN.md`/`plan.html` 的"最近变更"里要留痕）。用户不用自己去翻 JSON，直接看这两个文件就知道现在该练什么。

## 数据目录

固定使用 `~/Documents/fitness-plan-agent-data/`，六个文件：

| 文件 | 内容 |
|---|---|
| `profile.json` | 用户档案：身高/体重/目标/训练轨道/器械/伤病或体质限制 |
| `moves_library.json` | 动作库：每条 = 动作结构化信息 + 来源视频 + 示范图链接 + 当前排课状态 |
| `training_plan.json` | 结构化的当前计划数据（两条轨道 + 变更历史），机器读写用 |
| `CURRENT_PLAN.md` | 给用户看的纯文字计划，每次更新都重新生成 |
| `plan.html` | 给用户看的**单页应用**（可视化计划 + 编辑档案表单），每次更新都重新生成并重新发布 Artifact |
| `intake_log.md` | 每次处理一个新链接的过程记录（识别结果、判定、最终决定），用户可读可纠错 |

首次运行时，若目录下没有这些文件，先执行「Step 0 建档」再继续。

**多用户**：这是本地文件方案，不是云端服务，每个人各自在自己的 Claude 里跑这个 Skill、各自有一份 `~/Documents/fitness-plan-agent-data/`，互不干扰。`plan.html` 链接可以发给任何人自助建档，但生成的 `profile.json` 需要对方自己带回自己的 Skill 环境里，不会自动汇总到你这边。

## Step 0：建档（仅首次或用户要求更新时）

两种方式任选：

1. **发链接自助填写（推荐，多人共用同一个 Skill 时用这个）**：把 `plan.html` 的 Artifact 链接发给用户，让对方点"编辑档案"标签，填身高/体重/目标/训练轨道/器械/伤病限制，提交后下载一份 `profile-<昵称>.json`。数据全程留在对方浏览器本地，不经过任何服务器。拿到文件后，把内容存成 `~/Documents/fitness-plan-agent-data/profile.json`。**首次建档时页面里的 `PROFILE` 对象还是空/占位数据，等这一步做完、拿到真实数据后，要把 `PROFILE` 更新成真实值再重新发布，不然"编辑档案"标签下次打开预填的还是占位数据。**
2. **直接对话问**（单人快速用，或用户没法打开链接时）：简短几轮问完，不用一次问全部。

### `training_modes` 不是人设标签，是两条可以同时存在的轨道

**重要**：不要把"规律训练"和"懒人模式"当成用户的固定人设去二选一——同一个人完全可能这周有空规律训练，下周很忙只能应付几分钟。`profile.json` 里的 `training_modes` 是一个数组，可以同时包含 `"structured"` 和 `"lazy"`，两条轨道各自维护自己的排课逻辑，互不冲突：

- **`structured`（规律课表）**：`profile.structured = {days_per_week, session_minutes}`，按周排固定天数的课表。
- **`lazy`（懒人应急池）**：`profile.lazy = {session_minutes, scenes}`。**核心不是"挤时间做一个动作"，而是"绑定场景"**——`scenes` 是用户每天肯定会出现的地方（床上/沙发客厅/办公桌前/厨房台面/楼梯间走廊/通勤排队，也可能是自定义场景）。逻辑是：场景是触发器，动作可以很简单，但要固定绑定在场景上，靠"反复出现"攒积累，而不是靠单次强度或凑时间。`session_minutes` 存的是"在场景里愿意花的时长"，不代表动作难度。

一个人可以两条轨道都开：健身房有空的时候走 `structured`，忙的时候走 `lazy` 应急，两份都活在同一份 `training_plan.json` 里，不是二选一切换的两个"模式"。

```json
{
  "nickname": "小茜",
  "height_cm": 165,
  "weight_kg": 60,
  "goals": ["减脂", "塑形"],
  "training_modes": ["structured", "lazy"],
  "structured": { "days_per_week": 3, "session_minutes": 40 },
  "lazy": { "session_minutes": 10, "scenes": ["床上", "沙发/客厅", "办公桌前"] },
  "equipment": ["哑铃", "瑜伽垫"],
  "limitations": ["膝盖旧伤，避免深蹲负重过大"],
  "updated_at": "2026-08-18"
}
```

只开一条轨道时，另一条对应字段为 `null`（比如只想懒人应急：`"training_modes": ["lazy"], "structured": null`）。

## Step 1：抓取视频

用户发来一个或多个视频链接。按平台选抓取方式：

- **YouTube / B站**：优先用官方字幕/CC 转写（有现成接口/可通过 WebFetch 拿到字幕文本），拿不到再退化成视频简介 + 标题。
- **小红书 / 抖音，第一层**：WebFetch 直接请求分享链接，有时能拿到标题/正文文案/时间戳列表（实测有成功案例，也有失败的，不保证）。
- **小红书 / 抖音，第二层（第一层拿不到有效信息时，优先用这个，别直接跳去问用户要截图）**：WebFetch 只读网页文字摘要，不解析视频画面/音频，也不返回视频文件直链。这种情况下换成**下载视频 + 关键帧读图 + 音频转写**，两路一起上，实测比纯文字抓取的细节多得多（连组数次数、具体发力口诀都能读到，`confidence` 可以标 `high`）：
  1. 用 Bash `curl` 直接抓分享链接重定向后的原始页面 HTML（不走 WebFetch，因为要的是嵌在页面 JSON 里的视频文件直链，WebFetch 的摘要会把这类内容过滤掉）。带一个移动端 UA（如 iPhone Safari UA）。这是"别用 Bash 做网络查资料"这条习惯的一次刻意例外，原因是这个需求（拿二进制视频文件）本来就不是 WebFetch 能做的事，不是图省事绕开工具。
  2. 在 HTML 里搜 `masterUrl` / `backupUrls` / `.mp4` 之类的字段，拿到带签名的视频直链（小红书是 `sns-video-*.xhscdn.com/.../*.mp4?sign=...`，抖音等平台字段名可能不同，需要现场找）。
  3. `curl` 把视频下载到 `/tmp`。
  4. **画面**：`ffmpeg -vf "select='gt(scene,0.25)',scale=720:-1" -vsync vfr` 按镜头切换抽取关键帧（几十秒的视频一般十几到二十张关键帧就够，太多再调高 scene 阈值精简；如果视频是单镜头到底、scene 检测抽不出几张，改用 `fps=1` 固定间隔抽帧）。用 Read 工具逐张读关键帧图片，把画面里的文字（动作名、组数次数、发力要点）摘出来，原文照抄，不要在没读到的地方脑补。
  5. **音频**：`ffmpeg -vn -ar 16000 -ac 1 -c:a pcm_s16le` 把音轨转成 wav，用 `whisper-cli -m ~/.whisper-models/ggml-small.bin -f <wav> -l zh` 转写。这台机器已经装好了模型（见下方"依赖"），不用每次重新下载。**whisper 在纯静音/背景噪音上会瞎编内容**（幻觉），转写结果如果和画面内容对不上、或者是奇怪的重复句子，别采信，当作没转出来处理。
  6. 画面和音频两边只要有一边给出有效信息就够；都没有的话（纯跟练、无字幕、无有效讲解音频），如实标 `confidence: low`，把已经确认的信息（比如从画面动作判断出的大致动作类型）和"未确认"的部分分开写，不要编。
  7. **处理完立刻删掉所有临时文件**（下载的视频、wav 音频、抽出来的帧图），不管成功还是失败都要删，不要把这些留在 `/tmp` 或项目目录里——**项目数据目录只存文字结果，不存视频/音频等二进制文件**，这是硬性要求，不是可选项。
  8. 如果这套流程失败（拿不到直链、下载被拒、平台改了结构），才退回**第三层**：直接问用户要几张关键帧截图，让他们手动发给你读，或者让用户口述视频内容。

**依赖**（一次性本地安装，免费，不产生任何费用，纯离线跑在用户自己电脑上）：
- `ffmpeg`（抽帧、转音频）、`whisper-cli`（whisper.cpp，语音转写）—— 用 `which ffmpeg` / `which whisper-cli` 确认是否已装，没装用 `brew install ffmpeg whisper-cpp`。
- 语音模型：`~/.whisper-models/ggml-small.bin`（约 500MB，多语言，中文够用）。没有就用 `curl -sL "https://huggingface.co/ggerganov/whisper.cpp/resolve/main/ggml-small.bin" -o ~/.whisper-models/ggml-small.bin` 下载（先 `mkdir -p ~/.whisper-models`）。**不要用 `brew install whisper-cpp` 自带的测试占位模型**（文件名类似 `for-tests-ggml-tiny.bin`，跑起来很快但转写永远是空的，踩过一次坑）。

## Step 2：识别动作，结构化

把抓到的文本喂给自己（LLM 推理），抽取成一条记录，写入 `moves_library.json`。**`id` 生成前先读一遍 `moves_library.json` 里已有的最大编号，不要按日期直接猜下一个数字**——同一天处理多批链接容易撞号（踩过一次坑：两条不相关的动作都被编成了 `move_2026-08-19_002`，其中一条覆盖了另一条在 `training_plan.json` 里的引用，排查了才发现）。

```json
{
  "id": "move_2026_08_18_001",
  "name": "臀桥（Glute Bridge）",
  "source_url": "https://...",
  "platform": "xiaohongshu",
  "collected_at": "2026-08-18",
  "key_points": ["脚跟发力，不是腰发力", "顶部夹臀 1-2 秒", "避免腰部代偿"],
  "target_muscles": ["臀大肌", "腘绳肌"],
  "suitable_for": ["新手", "膝盖不好的人"],
  "equipment_needed": [],
  "difficulty": "入门",
  "demo_gif_url": null,
  "confidence": "high",
  "schedule_status": "待判定"
}
```

如果文案信息不够（比如只给了动作名和时间戳，没展开讲解要点），如实标记 `"confidence": "low"`，`key_points` 里写"以下为通用做法提示，非原视频讲解"，不要编造成好像是博主原话。

## Step 3：找示范图/GIF（引用现成资源，不生图）

用识别出的英文动作名 + "exercise gif/demonstration" 去搜索（WebSearch/WebFetch），优先引用有开放示范图库的站点（如 ExerciseDB、MuscleWiki 等同类资源）。找到就把链接存进 `demo_gif_url`；找不到就存 `null`，回复里用文字描述代替，不要虚构链接。**如果这条动作最终没有排进任何一条轨道（Step 4 判定不匹配），可以跳过这一步，等用户明确要保留时再补。**

## Step 4：查重 / 冲突过滤

新动作进来后，对照 `moves_library.json` 和 `training_plan.json` 做三层检查，按顺序判断：

1. **同一动作的不同来源重复**：`target_muscles` + 动作模式高度相似（如都是"深蹲变式"）→ 判断两条讲解谁的要点更完整、更适合该用户的水平，保留一条，把另一条标记 `superseded_by` 存档（不删除，留痕）。
2. **计划编排冲突**：新动作会不会导致同一天同一肌群安排过量，或和已排的动作强度/节奏矛盾 → 需要时调整该动作被安排的日期，而不是直接拒绝这个动作。
3. **与用户情况不匹配**：对照 `profile.json` 的 `limitations`、`equipment`，以及每条**已开启**轨道各自的条件（`structured` track 主要看器械/伤病限制；`lazy` track 额外要看动作能不能在 `lazy.scenes` 里的场景做）→ 分两种情况，处理方式不一样：
   - **硬冲突**（明确需要健身房专业器械/龙门架/绳索训练器这类家里不可能有的，或者踩了 `limitations` 里的伤病禁忌）：直接按最合理的方式处理（存进动作库但不排课 / 换成能满足条件的替代动作 / 跳过），处理完在总结里说明"这条不匹配，我做了 XX 处理，为什么"，不用停下来等确认。
   - **软冲突/器械清单里没写但家里大概率有或不贵的东西**（脚踝沙包、椅子、毛巾、泡沫轴这类）：**宽进**——直接排进计划，同时在动作的 `note` 里清楚标注"需要 XX，你的器械清单里没有这项"，然后**问用户**要不要保留（她可能家里其实有、或者愿意买，器械清单本身未必是穷举完的）。这一类是明确要问的例外，不算违反"有依据的决策直接做"的原则——因为器械到底有没有，只有用户自己知道，我判断不了。
   
   **一个动作可能适合 `structured` 但不适合 `lazy`（比如需要杠铃的动作塞不进沙发场景），这种情况下只排进适合的那条轨道，不用两条轨道整体通过或整体拒绝。**

每次判断都写一行到 `intake_log.md`，让用户能看到 AI 到底是怎么筛的。

## Step 5：更新训练计划（两条轨道 + 记忆）

`training_plan.json` 结构：

```json
{
  "structured": {
    "days": {
      "周一": [{ "move_id": "move_xxx", "sets_reps": "3组 x 12次" }],
      "周三": [],
      "周五": []
    }
  },
  "lazy": {
    "pool": {
      "沙发/客厅": [{ "move_id": "move_xxx", "note": "顺手做的固定动作" }],
      "床上": []
    }
  },
  "changelog": [
    {
      "date": "2026-08-18",
      "move_id": "move_xxx",
      "move_name": "...",
      "action": "added_to_structured | added_to_lazy | added_to_both | replaced | skipped_mismatch | skipped_duplicate",
      "reason": "一句话说明为什么这么处理"
    }
  ]
}
```

处理逻辑：

1. 对通过 Step 4 筛选的动作，**分别判断**它适合 `structured`、`lazy`，还是两条都适合，还是都不适合（都不适合时只留在动作库，不动 `training_plan.json`）。
2. **`structured` 轨道**：按 `days_per_week` 分天排进 `days`，兼顾肌群轮换和 `session_minutes` 时长，给出组数/次数建议。
3. **`lazy` 轨道**：给 `lazy.scenes` 里的每一个场景配 **1（最多 2）个固定动作**，不要甩一堆选项让用户临场挑——选择太多本身就是"没坚持下去"的常见原因。动作要匹配场景的物理条件（"床上"配平躺拉伸/核心静态动作，"办公桌前"配坐姿/站姿动作，"楼梯间"配爬楼梯变式，不要把需要器械或大幅度动作的东西塞进"床上"）。如果某个场景已经有固定动作了，新动作只有在明显更合适时才替换（同样走 Step 4.1 的"谁更好"判断），不是无脑往里加。
4. 每次处理，不管排没排进计划，都在 `changelog` 里追加一条记录——**这就是"记忆"**：用户能看到"为什么这周计划变了"或"为什么这条视频没进计划"，而不是每次都是全新生成、看不出历史。`changelog` 只追加，不覆盖删除。
5. 处理完，**重新生成 `CURRENT_PLAN.md`**（覆盖写，因为它是当前状态的完整呈现，历史变更由 `changelog` 保留）。格式大致如下：

```markdown
# 当前训练计划

更新时间：2026-08-18

## 📅 规律课表
### 周一
- 深蹲变式 — 3组 x 12次（[要点] / [示范图链接]）
### 周三
...

## 🛋️ 懒人应急池
### 沙发 / 客厅
- 顺手做的固定动作：... （每次约 10 分钟）
### 床上
- 暂无匹配动作

## 最近变更
- 2026-08-18：龙门架 W 下拉等 5 个动作评估后未采纳（需要健身房器械，与沙发/客厅场景不匹配）
- 2026-08-18：...
```

如果这次处理的动作**一个都没能排进计划**（比如今天演示的龙门架系列），`CURRENT_PLAN.md` 的计划部分保持不变，只在"最近变更"里加一行说明评估过但没采纳、为什么——**不匹配就不更新，但要让用户知道系统评估过了，不是漏掉了**。

## Step 6：同步更新 `plan.html`（单页应用，计划 + 编辑档案）

`CURRENT_PLAN.md` 更新的同时，`plan.html` 也要跟着更新，内容必须一致，不能一个改了一个没改。

**做法**：不要每次从零设计页面，用已有的 `~/Documents/fitness-plan-agent-data/plan.html` 当模板，只改文件里的两个数据对象，页面其余的 CSS/HTML/JS（身体示意图渲染逻辑、编辑表单、卡片预览、标签切换）都不用动：

- **`PROFILE`** —— 必须和 `profile.json` **完全一致**。这是"编辑档案"标签预填表单用的数据源，是纯前端内存对象，不经过 URL 参数、不经过服务器。改完 `profile.json` 忘了同步改这里，用户点"编辑档案"看到的就是过期数据。
- **`PLAN`** —— 对应 `training_plan.json` + `moves_library.json` 里已排入计划的动作，改 `nickname / goals / tracks_active / structured / lazy.scenes / changelog`。
- **肌肉松解 & 康复建议板块**（`renderRecovery` 函数，`MUSCLE_RECOVERY` 表）——不需要单独维护数据，自动从 `PLAN.structured` + `PLAN.lazy.scenes` 里已排入动作的 `target_muscles` 去重算出来，每个肌群配一个放松/拉伸动作，如果 `PROFILE.limitations` 有内容还会在顶部提示"已经按你的伤病史给了针对性提示"。**新出现的肌群词如果不在 `MUSCLE_RECOVERY` 里，顺手补一条**（拉伸动作 + 做法，不需要的话 `caution` 留 `null`），跟 `MUSCLE_MAP` 一样用的是 `moves_library.json` 里 `target_muscles` 同一套词，不用重新设计新字段。
- **`LIBRARY`** —— **完整的 `moves_library.json`**，不只是排进计划的那几条。页面上有一个独立的"动作库"板块，把所有识别过的动作按 `schedule_status` 分组显示（已排入 / 待定（缺器械、待确认等）/ 不采纳（重复、硬冲突）），每条一行：名称 + 一句话状态原因 + 链接（如果有）。**用户要能在页面上看到系统识别过的全部动作，不只是最终进了计划的那几个**，不然像"宽进但待确认"这种中间状态的动作，用户根本没地方看到、没法确认。
  - "待定"分组里每条前面有个勾选框，加一个"复制选中清单"按钮（`renderLibrary` 函数已经实现），用户勾选想加入计划的动作、点复制，会生成一段"请把以下动作加入训练计划：- xxx - xxx"的文字到剪贴板，粘贴发回来就是一份现成的处理请求，不用她自己重新打字列名字。这个功能改 `LIBRARY` 数组时会跟着自动生效，不用每次手动改。

关键点：
- 人体高亮**不用手画**，`MUSCLE_MAP` 已经把中文肌群名（跟 `moves_library.json` 里的 `target_muscles` 字段是同一套词）映射到身体分区和 front/back 视角，写 `target_muscles` 数组，图会自动生成对应部位高亮。新出现的肌群词如果不在 `MUSCLE_MAP` 里，先补一条映射，别让它掉进默认分区。
- `PLAN.structured` 为 `null` 时用现成的"未开启"占位块（模板里已经有），别硬造假数据填满。
- `changelog` 数组和 `training_plan.json` 的 `changelog` 保持同步，最新的放最前面。
- 改完用 Artifact 工具重新发布**同一个文件路径**（保持同一个 URL 不变，用户不用重新收藏新链接），并把链接同步更新到 `CURRENT_PLAN.md` 顶部。
- 图里引用的示范资源（`demo_gif_url` 等）**只能做成可点击的外链文字**，不能直接 `<img>` 嵌外部图片。Artifact 环境的 CSP 会挡掉外部图片/字体等资源加载，只有内联 SVG/CSS/JS 能正常工作。
- **每个动作卡片必须带一个可点的参考链接**（`buildMoveCard` 已经支持 `move.link` / `move.link_label` 字段），人体示意图只标目标肌群、不足以学会怎么做，用户需要真能点进去看：
  - 来自真实收藏视频的动作（`moves_library.json` 里 `source_url` 不为空）→ `link` 直接用那个 `source_url`，`link_label` 写"看原视频（平台名）↗"。
  - AI 自己想的替代动作（`source_url` 为空）→ 按 Step 3 的方法去 WebSearch/WebFetch 找一个可信的示范参考（ExerciseDB、MuscleWiki、ExRx.net 这类），存进 `moves_library.json` 的 `demo_gif_url`，`plan.html` 里同步填 `move.link`。
  - 两边都没有的动作，`buildMoveCard` 会自动显示"还没有参考链接"的提示，不要留空不管，处理完这批动作前尽量把链接补齐。
- **这一份文件同时占两个 Artifact URL**（当初分开建的建档表单链接和计划链接，现在都发布同一份合并内容，两个链接打开效果一样），重新发布时两个文件路径都要发一遍，别漏了。发布时都要带 `capabilities: {downloads: true}`，不然"下载 profile.json"按钮不能用。

## 交互原则

- 写给用户看的文案（`CURRENT_PLAN.md`、`plan.html`、对话回复）**不要用"——"这种破折号**，读起来太像 AI 生成的。该断句就用逗号或句号，需要强调另起一句话就行。
- **有依据的取舍（器械匹配、场景匹配、来源可信度更高）直接做决定，不要每个动作都停下来问用户"要不要"**——用户明确反馈过这类决策要的是执行力。做完用一两句话说明选了什么、为什么，把否决权留给用户。真正该问的是信息不够判断、或后果不可逆/代价高的情况（比如彻底不确定内容是真是假、要不要装新工具/花用户的钱、器械清单里没写但用户可能其实有的东西，见 Step 4.3 的"软冲突"）。
- **"档案里没写这个器械" ≠ "用户没有这个器械"**——`profile.json` 的 `equipment` 是用户建档时填的，不是穷举清单。遇到清单外但常见/不贵的器械（沙包、椅子、毛巾……），默认**宽进**排入计划，而不是默认排除，处理方式见 Step 4.3。
- 抓不到字幕、动作信息不全，如实标 `confidence: low`，不要脑补硬编内容本身，但"要不要采纳/怎么处理"这个决策不用等用户拍板。
- 每次处理完一批链接，用一句话总结"新增了几个动作、去重了几个、有几个因为冲突没排进计划、`CURRENT_PLAN.md`/`plan.html` 有没有变化"，让用户一眼看到系统在做什么，并把 `plan.html` 的最新 Artifact 链接发给用户。
- 这是 MVP：抖音字幕抓取、复杂的周期化编排（力竭/渐进超负荷）暂不做，先把「链接进 → 结构化 → 去重冲突过滤 → 计划出」这条主链路跑顺。
